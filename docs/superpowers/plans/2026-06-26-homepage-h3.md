# Homepage Slice H3 — events-calendar block (implementation plan)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking. Use superpowers:test-driven-development for the pure date helpers (Task 1).

**Goal:** Add a reusable, CMS-placeable `events-calendar` homepage block that shows a month grid (`grid-cols-7`, event days tinted from `event.startAt`), an upcoming-events list with inline RSVP (reusing the existing `RsvpButton` + `lib/actions/rsvp.ts`), and a Subscribe/iCal link. Data comes from the existing `lib/events.ts fetchApprovedEvents()` — no new event-fetching infra.

**Architecture (grounded in the codebase):**
- The homepage is already a `blocks[]` page-builder (Slice H1). A new block must be registered in **THREE** places:
  1. `sanity/schema.ts` — import + add to the `schema.types[]` array.
  2. `components/blocks/index.tsx` — import + add to `componentMap`.
  3. `sanity/schemas/documents/homepage.ts` — add `{ type: "events-calendar" }` to the `blocks` `of:` list.
  - Plus the GROQ projection in `sanity/queries/homepage.ts` (the `homepageBlocksProjection` fragment) and the hand-edited `sanity.types.ts` (the "never run typegen" rule).
- `fetchApprovedEvents()` is `server-only`. So the **block component is an async server component** that fetches events + resolves auth, then renders a **client** child (`EventsCalendarClient`) for the interactive month-grid/RSVP (mirrors how server blocks like `all-posts.tsx` fetch data, and how `event-card.tsx` passes server-resolved `signedIn` + `labels` to keep the tree provider-free).
- Date math (month-grid construction + upcoming-filter) lives in a **pure, unit-tested helper** `lib/events/calendar.ts` (TDD), imported by the client component.
- iCal: **client-side `.ics` generation** (a Blob download from the already-fetched events) — no backend route. Documented as the scope decision (a server `/events.ics` feed is a follow-up).

**Tech stack:** Next.js App Router, TypeScript, Sanity, next-intl, Tailwind, shadcn/ui, Vitest.

## Task 1: Pure date helpers (TDD)

**Files:**
- Create: `lib/events/calendar.ts`
- Test: `lib/__tests__/events-calendar.test.ts`

**Interfaces:**
- `type MiniEvent = { _id: string; startAt: string | null }` (structural subset of `EventListItem`).
- `dayKey(d: Date): string` → `YYYY-MM-DD` (local) — the join key between a calendar cell and an event.
- `buildMonthGrid(year, month0): { date: Date; inMonth: boolean; key: string }[]` — a 6×7 = 42-cell grid (always full weeks), Monday-first, padded with leading/trailing days from adjacent months (`inMonth=false`). `month0` is 0-based (Jan=0).
- `eventDayKeys(events: MiniEvent[]): Set<string>` — set of `dayKey`s with ≥1 event (skips null `startAt`).
- `upcomingEvents<T extends MiniEvent>(events: T[], now: Date, limit: number): T[]` — events whose `startAt >= start-of-now's-day`, soonest-first, capped at `limit`; skips null `startAt`.

```typescript
import { describe, it, expect } from "vitest";
import { dayKey, buildMonthGrid, eventDayKeys, upcomingEvents } from "@/lib/events/calendar";

describe("dayKey", () => {
  it("formats a local date as YYYY-MM-DD", () => {
    expect(dayKey(new Date(2026, 5, 9))).toBe("2026-06-09");
  });
});

describe("buildMonthGrid", () => {
  it("returns a full 42-cell, Monday-first grid", () => {
    const grid = buildMonthGrid(2026, 5); // June 2026; June 1 is a Monday
    expect(grid).toHaveLength(42);
    expect(grid[0].key).toBe("2026-06-01");
    expect(grid[0].inMonth).toBe(true);
    expect(grid.filter((c) => c.inMonth)).toHaveLength(30);
  });
  it("pads leading days from the previous month (Mon-first)", () => {
    const grid = buildMonthGrid(2026, 0); // Jan 2026; Jan 1 is a Thursday
    expect(grid.slice(0, 3).every((c) => !c.inMonth)).toBe(true);
    expect(grid[3].key).toBe("2026-01-01");
    expect(grid[3].inMonth).toBe(true);
  });
});

describe("eventDayKeys", () => {
  it("collects day keys with an event, skipping null startAt", () => {
    const keys = eventDayKeys([
      { _id: "a", startAt: new Date(2026, 5, 9, 14).toISOString() },
      { _id: "b", startAt: null },
      { _id: "c", startAt: new Date(2026, 5, 9, 18).toISOString() },
    ]);
    expect(keys.has("2026-06-09")).toBe(true);
    expect(keys.size).toBe(1);
  });
});

describe("upcomingEvents", () => {
  const now = new Date(2026, 5, 15, 12);
  const evs = [
    { _id: "past", startAt: new Date(2026, 5, 10).toISOString() },
    { _id: "todayEarlier", startAt: new Date(2026, 5, 15, 9).toISOString() },
    { _id: "soon", startAt: new Date(2026, 5, 16).toISOString() },
    { _id: "later", startAt: new Date(2026, 5, 20).toISOString() },
    { _id: "nodate", startAt: null },
  ];
  it("keeps events from start-of-today onward, soonest-first, capped", () => {
    expect(upcomingEvents(evs, now, 2).map((e) => e._id)).toEqual(["todayEarlier", "soon"]);
  });
  it("includes same-day-earlier, excludes past + null", () => {
    const ids = upcomingEvents(evs, now, 10).map((e) => e._id);
    expect(ids).toContain("todayEarlier");
    expect(ids).not.toContain("past");
    expect(ids).not.toContain("nodate");
  });
});
```

## Scope decisions

- **iCal/Subscribe = client-side `.ics`** (Blob download from already-fetched approved events). No backend route. A server `GET /events.ics` subscribable feed is a documented follow-up — out of H3 scope (avoid inventing backend infra).
- **RSVP** reuses `components/events/rsvp-button.tsx` + `lib/actions/rsvp.ts` verbatim; block resolves `signedIn` to gate the control (matching `event-card.tsx`); the action self-authorizes regardless.
- **Region filter** (H3 outline's "optional region filter"): deferred — `fetchApprovedEvents()` has no region param and `event.relatedCommunity` is a reference (not projected). A region facet would need an extended fetch + projection; scoped out to keep H3 on calendar + list + RSVP + iCal. Noted as a follow-up.
- **Month paging** is client-only over the already-fetched set (`fetchApprovedEvents()` returns soonest-first up to 50), so paging needs no extra fetch.
